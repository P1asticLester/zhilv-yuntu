# UI 冒烟用例设计表（等价类 / 边界值 / 错误注入）

> **定位**：这是 `frontend/e2e/` 的**测试资产**，随仓库走，面试可以指着 GitHub 讲「用例是怎么设计出来的」。
> **口径**：10 条用例全部用 `page.route()` 打桩，**不碰真实后端 / 模型 / 高德 / 网络**；
> 不进 `backend/tests/` 的 pytest 收集，也不进 CI 默认门禁。
> 它证明的是「前端交互、渲染与错误态」，**不是完整 UI 自动化**，更不代表系统能扛真实流量。

## 1. 先说方法（面试被问「你怎么设计用例」就答这三句）

1. **等价类划分**：把输入按「系统会不会用不同方式处理」分组，每组挑一个代表，不必穷举。
   目的地分三类：`6 城本地攻略`（走 RAG 路径）、`省级 / 空值`（后端 422 拒绝）、`未沉淀城市`（动态候选池路径）。
2. **边界值**：在约束的边界上、边界外各取一个，而不是随便挑数。
   `travelers` 的 `min=1` → 取 `0`、`-1`；`budget` 的 `min=0` → 取 `-1`、`999999999`；日期取「结束早于开始」。
3. **错误注入**：不改产品代码，只在测试里让打桩的后端返回 422 / 502 / 延迟响应，
   看前端会不会弹提示、会不会停在首页、提交按钮的中间态对不对。

> 一个诚实的前提：`Home.vue` **没有写 JS 表单校验**，输入是原样 POST 给后端的。
> 所以边界值用例验的是「输入原样透传 + 后端拒绝时前端不崩」，**不是前端校验**。
> 这正是「先跑一遍看真实行为、再写断言」的结果，别在简历里写成「前端做了参数校验」。

> 还有一层更细的口径：⑦ 的 5 组边界值共用 `mode: "invalid_destination"` 打桩，
> 后端**无论收到什么都固定返回 422**，与输入值无关。因此这 5 组在「该值是否该被拒绝」
> 上没有区分度，本质是 1 条用例的 5 次数据驱动，验的是请求体保真与错误态呈现。
> **「该值是否该被拒绝」由接口层 `backend/tests/test_request_boundaries.py` 回答**：
> 同一组 5 个值用 `TestClient` 打真实 `TripRequest`，结论是 `travelers=0/-1`、`budget=-1`
> 返回 422；**日期倒挂与 `budget=999999999` 当前实现返回 200**（无跨字段校验 / 无上界），
> 这两处是已知校验缺口，写成断言是为了以后补校验时立刻红灯，不是假装已被拒绝。
> 所以准确说法是「**一张设计表两层落地**」，别写成「UI 层 10 条验证了参数校验」。

## 2. 覆盖矩阵（对应 `smoke.spec.ts` 的 10 条）

| # | 分组 | 输入 / 注入 | 预期 | 设计方法 |
|---|---|---|---|---|
| ① | 页面基线 | 直接打开 `/` | 标题「智能旅行助手」、目的地默认「大理」、提交按钮可用 | 冒烟（主流程可启动） |
| ② | 目的地有效等价类 | 「大理」+ 固定 200 响应 | 切到结果页，出现 `{city}旅行计划`、行程 ID、天气卡片 | 等价类代表值 |
| ③ | 天气等价类 A | 晴天天气响应 | tips 保留「注意防晒」，不出现雨提示 | 判定表分支 |
| ④ | 天气等价类 B | 雨天天气响应 | 增 2 条雨提示、过滤「防晒」 | 判定表分支 |
| ⑤ | 目的地无效等价类 | 「青海」+ 后端 422 | 弹「请输入具体城市」、停留首页 | 等价类 + 错误注入 |
| ⑥ | 目的地边界 | 空字符串 + 后端 422 | 同上 | 边界值 + 错误注入 |
| ⑦ | 数值 / 日期边界 | 5 组：日期倒挂、`travelers=0/-1`、`budget=-1/999999999` | 请求体原样透传（断言 postData），422 后停留首页 | 边界值 + 数据驱动参数化 |
| ⑧ | 中间态 | 响应延迟 1200ms | 按钮变「正在生成中...」且 disabled，随后结果页出现 | 状态迁移 |
| ⑨ | 外部依赖失败 | 后端 502 | 弹「上游服务不可用」、不切结果页 | 错误注入 / 降级 |
| ⑩ | 反向流程 | 结果页点「← 返回规划」 | 回到首页，结果页消失 | 场景法（往返） |

⑦ 是**一条 test 内参数化 5 组**：只注册一次 route，把 5 次请求体收集到数组里逐组断言，
避免反复注册路由导致 handler 叠加。5 组共用的 422 由打桩固定返回、与输入值无关，
所以断言的是请求体原样透传（前端没改值 / 没吞输入 / 没本地拦截），不是后端校验结果。
真实期望见 `backend/tests/test_request_boundaries.py`（接口层，8 条，同一组值）。

## 3. 明确未覆盖（别被问穿）

- **真实后端**：所有 `/trip/generate`、`/weather/forecast` 都是固定响应，验不到真实网络、部署配置、模型不确定性。要接真实后端需真 key + 模型费用，与 Step 5 同级单独拍板。
- **跨浏览器**：只用系统 Edge（`channel: "msedge"`），没跑 Firefox / WebKit。
- **视觉回归 / 可访问性**：没有截图基线、没有 a11y 断言。
- **完整数据流转**：保存 → 历史列表 → 导出这条链暂未覆盖（需要额外打桩 `/trip/save`、`/trip` 并核对 `History.vue` 渲染）。
- **登录态**：项目本来就没有鉴权，无此场景。
- **打桩与真实契约的偏差**：⑤ 省级「青海」在 UI 打桩里返回 422「请输入具体城市」，
  真实后端在无高德 key 时返回 **503 `city_resolution_unavailable`**；空目的地真实 422
  的错误体是路由层自定义 dict，不是 Pydantic 的 `detail` list。这些差异由接口层测试
  覆盖，UI 层仍按打桩契约验渲染，别把打桩响应当成后端事实。

所以准确说法是 **「做了 10 条 UI 冒烟（含等价类/边界值设计），没做完整 UI 自动化」**。
禁语：「UI 自动化覆盖全部流程」「前端做了参数校验」「这 10 条验证了真实后端」「UI 层这 5 组边界值验证了后端参数校验」。
